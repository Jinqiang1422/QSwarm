# 大模型集群任务接口扩展方案

> 版本：v2.1（新增任务模板库）｜ 前置：《QGC集群指挥控制二次开发方案.md》
> 配套交付：`src/Swarm/SwarmAIAgent.h/.cc`、`SwarmTaskController.h/.cc`、`SwarmTaskLibrary.h/.cc`、`SwarmAction.h`、`templates/`（内置模板）、`src/FlyView/SwarmAIPanel.qml`

---

## 1. 概述

在既有集群指挥控制能力之上，大模型（LLM）接口 v2 提供：

| 能力 | 说明 |
|---|---|
| 任务理解 | 自然语言 → 结构化动作，支持 Function Calling 与 JSON 两种对接方式 |
| 任务规划 | 单轮动作序列，或一次下发**多阶段任务**（起飞→搜索→返航） |
| 任务分配 | 机号分组（set_selection）+ 区域自动分带 + 编队槽位按 id 分配 |
| 任务状态机 | 阶段完成条件自动判定（含 MISSION_CURRENT 航线进度），自动推进 |
| 统一管线 | AI 规划与人工 Plan 视图设计共用同一套 MissionItem/上传通道/进度监控 |

两条铁律不变：**人在回路**（危险动作计划须人工确认）；**集群逻辑只在地面站**（不改 MAVLink/PX4）。

## 2. 架构（v2）

```
┌─────────────────────────── QGroundControl ───────────────────────────┐
│ SwarmAIPanel.qml：接口配置 / 对话 / 计划确认 / 任务状态机监视          │
│        │                                                             │
│  ┌─────▼──────────────┐   tools(chat/completions)   DeepSeek/Kimi/   │
│  │   SwarmAIAgent     │ ──────────────────────────► 通义千问/OpenAI/ │
│  │  · 态势上下文构建   │ ◄──────────────────────────  Ollama(本地)    │
│  │  · tools 定义/解析  │   tool_calls[] 或 JSON 文本（自动回退）       │
│  └─────┬──────────────┘                                            │
│        │ 理解结果（JSON 动作 / 多阶段任务）                          │
│  ┌─────▼───────────────────── 统一动作管线 ──────────────────────┐  │
│  │ SwarmManager::parseAndValidate()  白名单+限幅+机号校验        │  │
│  │ SwarmManager::executeActions()    动作→各子控制器             │  │
│  └─────┬───────────────┬──────────────────────┬─────────────────┘  │
│  ┌─────▼──────┐  ┌─────▼──────────┐  ┌───────▼───────────┐         │
│  │SwarmManager│  │Formation       │  │SwarmMissionPlanner│         │
│  │(集群指令)   │  │Controller(编队) │  │(区域覆盖规划)      │         │
│  └────────────┘  └────────────────┘  └─────────┬─────────┘         │
│  ┌──────────────────────────────┐              │                    │
│  │ SwarmTaskController(状态机)   │◄─────────────┘                    │
│  │ 阶段动作执行→条件监控→自动推进 │   MISSION_CURRENT / flightMode    │
│  └──────────────────────────────┘   / armed（与任务来源无关）        │
└────────────────────────────────────────────────────────────────────┘
```

关键解耦：**SwarmAIAgent 只负责"理解"**。动作校验/执行统一在 `SwarmManager`，
多阶段编排统一在 `SwarmTaskController`，三者共用 `SwarmAction` 结构——
人工面板、AI 单轮指令、AI 多阶段任务走的是同一条管线。

## 3. Function Calling（工具调用）

### 3.1 为什么升级

v1 让模型"输出 JSON 文本"：小模型/弱模型常夹带 markdown、漏字段、编造类型。
v2 把动作集注册为 **OpenAI tools**，模型通过原生 `tool_calls` 返回：

- 参数类型/枚举/必填由 JSON Schema 在协议层约束，格式漂移大幅降低；
- 参数校验、错误返回由服务端兜底；
- 一次返回多个 `tool_calls` 天然表达"动作序列"。

### 3.2 实现

- `SwarmAIAgent::_toolsJson()` 注册 **15 个工具**：13 个基础动作（set_selection/arm/takeoff/land/rtl/pause/start_mission/disarm/emergency_disarm/start_formation/stop_formation/plan_coverage/clear_missions）+ 2 个任务编排（start_swarm_task/abort_swarm_task）；
- 请求体：`tools` + `tool_choice:"auto"`；系统提示词只保留业务规则（`_systemPromptTools()`），格式契约完全交给 tools；
- 响应解析：遍历 `tool_calls[]`，`function.name` → 动作 type，`function.arguments`(JSON) → 参数，统一转成内部动作 JSON 后进入 `SwarmManager::parseAndValidate()`——**tools 只是更稳的"运输层"，校验/执行管线与 JSON 模式完全一致**；
- `plan_coverage` 的中心点参数改为可选 `center_lat/center_lon`（缺省=地图中心），规避工具 schema 对联合类型支持不一致的问题。

### 3.3 回退策略

- 面板配置区提供"工具调用"开关（持久化）：关闭后回到 v1 JSON 模式（`response_format: json_object` + 花括号容错提取）；
- 运行期自动兼容：模型忽略 tools 直接输出 JSON 文本时，按 JSON 路径解析；
- HTTP 400 且开启工具调用时，错误提示主动建议"该端点可能不支持 Function Calling"（典型：老版本 Ollama、部分代理网关）；
- 对话历史只保存**文本摘要**（不存 `tool_calls` 原始结构），避免后续请求因缺 tool 响应被严格端点（OpenAI）拒绝。

## 4. 任务状态机（SwarmTaskController）

### 4.1 模型

一个任务 = 有序阶段列表；一个阶段 = **一组动作 + 一个完成条件**：

```
任务「搜索后返航」
 ├─ 阶段1「起飞」    动作: takeoff(30)                     完成条件: all_airborne(≥25m)
 ├─ 阶段2「搜索」    动作: plan_coverage(...) + start_mission 完成条件: all_mission_finished
 └─ 阶段3「返航」    动作: rtl                            完成条件: all_disarmed
```

阶段进入 → 动作经统一管线执行 → 1 Hz 监控完成条件 → 满足自动进入下一阶段。

### 4.2 完成条件（complete_when.kind）

| kind | 判定（基于涉及机快照逐机检查，1 Hz） |
|---|---|
| `all_airborne` | 全部 armed 且相对高度 ≥ min_altitude（默认 3 m） |
| `all_disarmed` | 全部 !armed（降落完成） |
| `all_mission_finished` | 全部"曾进入 Mission 模式后退出"（MISSION_CURRENT 驱动的模式切换）或已降落上锁 |
| `formation_running` | 编队激活且僚机数 ≥ 涉及机数−1 |
| `duration` | 等待 seconds 秒 |
| `manual` | 等待操作员点"继续"（关键节点人工把关） |

`all_mission_finished` 采用"先观察到进入 Mission 模式，再观察到离开"的双边沿判定，
杜绝动作刚下发、飞机尚未切模式时的误判；每阶段有 3 秒宽限期与 600 秒超时（可调），
超时判任务失败并全体暂停悬停。

### 4.3 与任务来源无关（统一监控）

监控的是各机 `flightMode`（对照 `missionFlightMode`）、`armed`、相对高度——
**不关心任务是谁上传的**：AI 经 `plan_coverage` 上传的、或人工在 Plan 视图绘制上传的，
对状态机完全同构。人工任务同样可以手动触发"开始任务"后由状态机接管监控推进。

### 4.4 操作员控制

面板任务状态区显示：任务名、阶段清单（✓完成/▶当前/○待办）、状态文本；
`[中止任务]`随时可用（自动 pauseAll 悬停等待接管）；`manual` 阶段出现`[继续]`按钮。

## 5. 统一任务管线（AI 规划 ≡ 人工规划）

| 层 | 人工路径 | AI 路径 | 是否同一套 |
|---|---|---|---|
| 任务表示 | Plan 视图拖拽生成 MissionItem | `SwarmMissionPlanner::buildCoverageMissionItems()` 生成 MissionItem | ✅ 同一 `MissionItem` 类（TAKEOFF→WAYPOINT→RTL，GLOBAL_RELATIVE_ALT_INT 帧） |
| 上传通道 | MissionController → `writeMissionItems()` | `SwarmMissionPlanner` → 同一个 `writeMissionItems()` | ✅ 同一函数（QGC 源码 MissionController.cc 第 253 行） |
| 地面站缓存 | 上传后 PlanManager 持有 | 上传完成（`sendComplete`）后自动 `loadFromVehicle()` 回读 | ✅ Plan 视图可显示并继续人工编辑 AI 任务 |
| 执行 | "开始任务"按钮 → `startMission()` | `start_mission` 动作 → `startMissionAll()` | ✅ 同一 Vehicle API |
| 进度监控 | QGC 单机 MISSION_CURRENT 显示 | 状态机 `all_mission_finished` 判定 | ✅ 同一 flightMode/currentIndex 数据源 |

工程上落为三点代码事实：
1. `SwarmMissionPlanner` 拆出纯构建函数 `buildCoverageMissionItems()`（可预览/可测试），与上传解耦；
2. 上传成功后经 `Qt::SingleShotConnection` 挂接 `sendComplete`，回读同步并维护 `missionStatus`（各机任务项数）；
3. `SwarmManager::parseAndValidate/executeActions` 是唯一动作入口，AI 与人工殊途同归。

## 6. 任务模板库（SwarmTaskLibrary）

### 6.1 设计

常用多阶段任务存为 **JSON 模板文件**，人工可直接执行，AI 按名引用：

- **模板目录**：`QStandardPaths::AppDataLocation/SwarmTemplates/`，面板"打开目录"直达，可手工增删改后点"刷新"；
- **内置模板**：首次启动自动落盘 4 套，落盘后与用户模板同等待遇（可编辑，不可删除）：

| 模板 | 阶段编排 | 参数 |
|---|---|---|
| 区域搜索后返航 | 起飞(all_airborne)→区域覆盖+开始任务(all_mission_finished)→返航(all_disarmed) | 高度/长宽/角度/行距等 6 项 |
| 编队巡航后返航 | 起飞→编队(formation_running)→巡航计时(duration)→停止编队+返航 | 高度/长机/队形/间距/巡航时长 |
| 快速出动待命 | 起飞→待命(manual，等待人工) | 高度 |
| 全员返航降落 | 停止编队+返航(all_disarmed) | 无 |

- **参数化**：动作与完成条件中的 `"${key}"` 占位符在实例化时按参数表代入（带默认值与 min/max 限幅，
  字符串数字自动转数值）；仓库 `templates/` 目录附 4 套内置模板的参考副本。

### 6.2 AI 引用（run_task_template）

- 上下文注入：每条用户消息的 `[当前态势]` 新增 `templates` 摘要（名称/用途/参数默认值/阶段数）；
- 新增工具：`run_task_template{name, parameter_values}`——提示词规则要求**意图与模板匹配时优先引用模板**，
  不匹配才用 `start_swarm_task` 自定义编排；
- 执行链：模板实例化 → `SwarmTaskController::parseStages`（统一校验，已从 AI 私有下沉为公共方法）→
  挂起为待确认计划（**模板执行同样过人在回路确认**）→ `startTask`；
- JSON 回退模式对应动作：`{"type":"run_task_template","name":"...","parameter_values":{...}}`。

### 6.3 人工使用

面板"任务模板库"区列出全部模板：名称/阶段数/内置标记/用途说明，按 `parameters` 动态生成参数表单，
改参后点"执行"（操作员点击即确认，经统一校验后启动状态机）。用户可把自己的多阶段任务存成模板
（`saveTemplate`），沉淀组织级的标准作业流程。

## 8. 安全设计（在 v1 基础上新增）

| 机制 | 说明 |
|---|---|
| 阶段数/动作数上限 | 单任务 ≤ 8 阶段，单轮 ≤ 10 动作，防失控输出 |
| 阶段宽限期+超时 | 3 s 宽限防误判；600 s 超时判失败并全体悬停 |
| 中止即悬停 | abort() 自动 pauseAll，机群停在原地等待人工接管 |
| manual 条件 | 关键阶段可强制人工确认后才推进 |
| 双边沿任务判定 | 必须"先见 Mission 后见退出"，杜绝虚假完成 |
| 历史协议净化 | 不存 tool_calls 结构，避免触发严格端点 400 |

v1 机制（动作白名单、参数限幅、机号校验、人在回路确认、HTTPS/内网隔离、机载保护不旁路）全部保留。

## 9. 验证脚本（SITL 三机）

**工具调用模式**
1. 配置端点/Key，确认"工具调用"开启，测试连接成功。
2. 输入 `全体起飞到30米` → 面板显示计划（危险警示）→ 确认执行。
3. 输入 `全体起飞到30米，把当前区域搜一遍200乘150行距20，搜完返航`
   → AI 应返回**多阶段任务**（起飞→搜索→返航）→ 确认 →
   观察状态机：三机升空前条件不满足 → 全部升空后自动进入"搜索"（自动上传+开始任务）→
   三机依次退出 Mission 模式后自动进入"返航" → 全部上锁 → 任务完成。
4. 阶段清单的 ✓/▶ 标记随推进实时变化；中途点"中止任务"验证全体悬停。

**回退模式**
5. 关闭"工具调用"，重复步骤 3（JSON 模式），行为应一致。

**统一管线**
6. AI 上传区域覆盖任务后，切到 Plan 视图：应能看到并编辑该任务（同一套任务）；
   人工在 Plan 视图改一个航点后用 QGC 自身"上传"，再回 Fly 视图由状态机继续监控。

**多轮修正**
7. 任务运行中输入 `中止当前任务`，观察 abort_swarm_task 生效。

**任务模板库**
8. 面板模板库区点"执行"内置模板「快速出动待命」→ 三机升空后停在 manual 阶段 → 点"继续"结束。
9. 输入 `按区域搜索模板来一遍，高度40，区域300乘200` → AI 应调用 run_task_template
   （聊天区显示"已按模板「区域搜索后返航」生成 3 阶段任务计划"）→ 确认 → 状态机逐阶段推进。
10. 模板目录中手工新增一个 JSON 模板 → 面板"刷新"→ 列表出现新模板，AI 下一轮即可引用。

## 10. 故障排查（新增）

| 现象 | 排查 |
|---|---|
| HTTP 400 且提示工具调用 | 端点不支持 tools → 关闭"工具调用"开关 |
| 模型只回文字不调用工具 | 模型太弱或提示词理解差：换模型；或检查是否误在 JSON 模式 |
| 任务卡在"搜索"阶段 | 某机未进入 Mission 模式（未成功 start_mission）：查该机状态；超时后会自动失败并悬停 |
| 计划里没有 start_swarm_task | 指令未体现先后依赖；明确说"……完成后……"触发多阶段编排 |
