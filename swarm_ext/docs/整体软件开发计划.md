## 2. 差距分析与关键决策

### 2.1 四类差距汇总

1. **功能差距**：目标域 2（感知态势）整块空白；目标域 3 的多候选方案、高级约束校验、仿真预演、动态重规划待补；目标域 1 的 RAG 接地与本地化部署待验证。
2. **架构差距**：当前全部为 QGC 进程内实现（单体），与目标框架"QGC 是壳，不是全部"的微服务解耦原则存在差距——但属于**有意识的阶段选择**，见 2.2 决策。
3. **安全与可信差距**：审计追溯、防注入、L1/L2/L3 自主分级未形式化（当前实际运行档位 ≈ L2）、幻觉率/准确率无量化基线。
4. **验证差距**：无自动化场景库、无 LLM 评测集、无对比基线实验，量化指标全部待首测。

### 2.2 架构演进决策（单体 → 伴生微服务）

**决策 D1（P1~P2 保持 QGC 进程内实现）**：当前功能迭代期，内嵌实现迭代最快、调试最简单、SITL 验证链最短；过早引入分布式会拖慢认知层功能的试错节奏。

**决策 D2（接口契约先行）**：动作 Schema（16 工具）、态势上下文 JSON、任务状态机事件、模板 Schema 已具备稳定 JSON 形态——P1 将其文档化冻结为 **Swarm API v1 契约**，使后续服务化成为"换传输层、不换语义"。

**决策 D3（P3 感知先行服务化）**：视频检测/航迹融合是计算密集且天然独立的功能，P3 起以独立进程（地面 GPU）实现，经 gRPC/消息总线与 QGC 交互，这是服务化的第一个验证点。

**决策 D4（P4 认知/规划服务外移，校验闸门永驻 QGC）**：AI 与规划服务外移为 MAVSDK-Server + gRPC sidecar；但**确定性校验闸门（白名单 + 约束引擎）永久驻留 QGC 进程内**——这是安全红线：任一服务崩溃时，QGC 原生多机手动模式自动兜底，面板显著提示，链路不受影响的只有"智能"，永远不是"安全"。

### 2.3 三条设计原则的工程落点

| 原则 | 工程落点 | 状态 |
| --- | --- | --- |
| 大模型不直接控飞机 | LLM 只产出工具调用 → parseAndValidate → executeActions；校验层与 LLM 进程/代码路径严格分离 | 已落地，P2 加固 |
| QGC 是壳，不是全部 | 核心侵入 <5%（6 处追加式补丁）；P3/P4 逐步服务化 | 部分落地 |
| 自主等级可分级 | AutonomyLevel（L1 仅建议 / L2 监督执行 / L3 限定域自主）形式化 + 进入退出条件 | P1 形式化，P4 实现 L3 |

## 3. 分阶段开发计划

总体节奏：**P0 已完成 → P1 工程硬化与安全底座 → P2 校验闸门与协同规划 → P3 感知融合与态势理解 → P4 闭环指挥与规模化 → P5 外场验证与本地化**。P1/P2 深化已建能力，P3 开辟感知新域，P4/P5 收敛验收。对照目标框架 M1~M5：M1（集群底座）与 M2（规划副驾核心）已在 P0 大幅提前完成，故整体里程碑前移。

### P0（已完成基线）

- 集群底座 + 大模型指挥接口 + 统一任务管线 + 状态机 + 模板库，见 1.1 节。
- 遗留技术债：无 CI、无自动化测试、无评测基线——全部转入 P1。

### P1 工程硬化与安全底座（6~8 周）

**目标**：把已建成能力做扎实、可度量、可回归；补齐安全目标的"地基三项"（审计、防注入、自主分级）。

| 工作包 | 内容 | 产出 |
| --- | --- | --- |
| WP1.1 审计追溯系统 | SwarmAuditLogger：全量记录"操作员输入 → LLM 原始输出 → 校验结果 → 下发指令 → 执行反馈 → 人工确认/放弃"，JSONL 落盘，会话 ID + 单调时间戳关联；支持按任务导出回放 | 审计模块 + 导出工具 |
| WP1.2 防注入与输入过滤 | 外部文本（目标上报、第三方数据）进入 LLM 前的注入模式过滤层；工具参数白名单复查加固；系统提示词与用户/外部数据隔离 | 过滤层 + 注入测试用例集 |
| WP1.3 自主分级形式化 | AutonomyLevel 枚举（L1/L2/L3）+ 各档位行为矩阵（哪些动作需确认、哪些禁止）+ 面板档位切换；当前实现归位为 L2 | 分级控制模块 + 行为矩阵表 |
| WP1.4 LLM 评测集 v1 | ≥500 条"指令-计划"标准对，覆盖 16 工具 + 4 模板 + 越界拒绝 + 多阶段任务；自动回归脚本，每次模型/Prompt 更新后运行 | 评测集 + 回归脚本 + **准确率/一次通过率基线首测报告** |
| WP1.5 SITL 场景库 v1 | ≥5 个 8 机场景（区域搜索、编队巡航、单机故障注入、链路退化、紧急中止）脚本化一键拉起；一键中止 ≤1s 实测 | 场景脚本 + 时延实测记录 |
| WP1.6 测试与 CI | 核心逻辑单元测试（动作校验、模板实例化、状态机迁移）；编译门禁 CI（Linux 构建 + 测试） | 测试套件 + CI 流水线 |

**退出标准**：① 全部下发动作 100% 进入审计链；② 评测集回归 CI 化并产出基线指标；③ 8 机场景一键复现；④ 一键中止实测 ≤1s。

### P2 校验闸门与协同规划进阶（8~12 周）

**目标**：把"校验闸门"从白名单升级为完整约束引擎；把规划闭环升级为"多候选 + 可编辑 + 可预演"。

| 工作包 | 内容 | 产出 |
| --- | --- | --- |
| WP2.1 约束校验引擎 v1 | 校验项：地理围栏/空域多边形、单机航程-剩余电量估算、机间间隔与 4D 航迹去冲突、通信链路覆盖、载荷能力匹配；不通过时输出具体违例项 + 修改建议 | 约束引擎（QGC 进程内，D4 红线） |
| WP2.2 多候选方案生成 | LLM 一次生成 2~3 个候选方案（含文字优劣说明）；方案对比视图（地图叠加 + 指标表） | 多候选协议 + 对比 UI |
| WP2.3 计划可编辑化 | LLM 计划导出至 QGC Plan 视图图形化微调，微调结果回写统一管线（保持"LLM 与人工同一套系统"承诺） | Plan 互通模块 |

| WP2.5 模板库扩充 | 新增扇形/平行扫掠、编队巡逻、多机接力跟踪、会合/集结；模板 Schema v2（标签、适用规模、载荷需求） | 模板 ≥9 套 |

**退出标准**：① LLM 计划一次通过约束校验率 ≥90%；② 集群任务规划耗时较人工基线缩短 ≥70%（实测）；③ ≥9 套模板可用。

### P3 感知融合与态势理解（12~16 周，对应 M3）

**目标**：建成目标域 2 全域能力；完成服务化解耦第一步。

| 工作包 | 内容 | 产出 |
| --- | --- | --- |

| WP3.2 检测跟踪服务 | YOLO 类检测 + 多目标跟踪，独立进程（地面 GPU，机载边缘为可选项）；结构化结果（类别/地理坐标/置信度/航迹 ID）经自定义 MAVLink（TUNNEL）或 gRPC 回传 | 感知服务（**第一个微服务**） |
| WP3.3 多源航迹融合 | 最近邻/JPDA 航迹关联 + 置信度加权去重 → 统一目标清单 | 融合引擎 |

| WP3.7 自定义 MAVLink 消息集 | 感知上报/航迹融合/计划元数据消息定义，纳入 dialect 统一管理 | dialect 扩展文件 |

### 4.2 验证评估专项

- **场景库**：P1 v1（≥5 场景/8 机）→ P4 扩展至 ≥10 场景、8/16/32 机回归（含动态目标跟踪、拒止环境）。
- **LLM 评测集**：P1 v1（≥500 条）→ 每阶段增补新工具/新模板用例，模型或 Prompt 任何变更强制回归。
- **递进路径**：SITL（P1~P4）→ 半实物 → 3~5 架实机 → 规模实机（P5），每级设准入准出。
- **对比基线**：P2 起建立人工基线数据（规划耗时），P5 完成全量人因对比。

### 4.3 工程与配置管理专项

- **git 分支模型**：master 保持稳定可集成；功能开发走 feature/* 分支，评审后合并；每个阶段打 milestone 标签（m1~m5）；当前已有 4 次提交作为 P0 基线。
- **上游同步**：QGC 上游设为 upstream remote，每季度 rebase 一次；定制改动收敛在插件层（当前 6 处追加式补丁，核心侵入 <5%），补丁文档随代码同步维护。
- **CI**：P1 建立编译门禁 + 单元测试；P2 起接入评测集回归；P4 起接入 32 机场景回归。
- **部署演进**：P1~P3 单体 QGC 定制构建 → P4 起 docker-compose 多服务编排。
